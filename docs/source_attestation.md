# Publication reports after manuscript-only working-tree changes

The default publication validator still requires the original clean Git identity.
An explicit source attestation supports completed campaigns whose recorded
revision is either the training commit or that same commit with `-dirty`, when
the author confirms that only writing/non-execution files changed during training.
This is an audit of provenance, not a change to selection or reporting criteria.

The original launcher did not save the contents of a dirty checkout. Current
source equality cannot reconstruct that history. The attestation therefore
records the author's statement separately from machine-verifiable evidence.
It does not strip `-dirty`, rewrite completion manifests, or manufacture a clean
historical revision.

## Checks

- Compare `src/`, `configs/`, `scripts/`, `legacy/`, dependency declarations and
  packaging inputs against the exact training commit. Reject added/deleted code
  and changed executable/configuration contents, including ignored source files.
  Generated bytecode/package metadata and the separately supplied legacy CSV
  are excluded. Revised forecast validation separately checks its historical
  input hashes, configuration, runtime and fitted artifact hashes.
- Separate the three reporting/attestation modules from execution identity and
  bind their current bytes. For `clearing_campaign.py`, only the
  `validate_forecast_fit` function may differ; all other AST nodes must match.
  This permits the validation fix, not changes to fitting or campaign behavior.
- Bind the exact run inventory, original Git identifiers, run completion
  manifests and forecast completion manifests. Existing full publication checks
  still validate all completion-bound artifacts, checkpoints, evaluation sizes,
  seed matrices, paired controls and canonical configurations.
- Verify the source and manifest bindings again before publishing the report.
  Training launchers and normal forecast reuse retain their existing strict
  behavior. The attestation is used only when explicitly supplied to reporting.

## Recorded v20 attestation

The author confirmed: “literally nothing affecting the runs has been changed.
I only added the paper back.” The main campaign contains 302 runs at
`354656645a7e035be718e03cbf100664d1a87262` and 138 at the same revision with
`-dirty`. The later `351d081` commit adds the paper and changes `.gitignore`.
This attestation covers the 440-run main campaign. The two 40-run follow-ups
already have separate reports and retain their own provenance records.

Create the attestation once (the command refuses to overwrite one):

```bash
.venv/bin/python -m lmm.experiments.source_attestation \
  --root results/revision_v20 \
  --training-revision 354656645a7e035be718e03cbf100664d1a87262 \
  --author-statement 'Only the manuscript was added back and its Git ignore rule changed during the campaign; nothing affecting simulation, fitting, training, selection or evaluation changed.'
```

Generate or regenerate the publication report without training or evaluation:

```bash
MPLCONFIGDIR="$PWD/.cache/matplotlib" \
.venv/bin/python -m lmm.experiments.make_report \
  --root results/revision_v20 \
  --seeds 42 7 99 123 2024 314 577 811 1618 2718 \
  --publication \
  --source-attestation results/revision_v20/_provenance/source_attestation.json
```

Output: `results/revision_v20/_publication/index.html`. The HTML, README and
report manifest disclose the attestation; `audit/source_attestation.json`
contains its full evidence. Existing development and legacy reports stay intact.
The numerical report tables are unchanged by provenance acceptance. After
further executable/reporting source changes, an old attestation must fail;
review and retain the old record before creating new provenance evidence.
